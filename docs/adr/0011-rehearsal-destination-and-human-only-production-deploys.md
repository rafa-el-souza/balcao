# ADR-0011: Rehearsal destination, production VM from M3, human-only production deploys

**Status:** accepted · **Date:** 2026-11-04 (text revised the same night,
before the first commit, after three independent reviews; amended
2026-11-09, before the first commit, for the MVP: see the last paragraph of
the decision) · Supersedes the first consequence of ADR-0006.

## Context

The owner's hosting budget is tight and the project may pause for weeks
at a time; a VM billed from M0 would charge for a placeholder page. The
code is written by a coding agent running unsandboxed in the owner's
development account, so the agent is a threat actor of its own (threat
model T8): whatever credentials and whatever executable code that account
can reach, a steered or runaway session can reach too. ADR-0006 assumed a
production host from M0, deploys "from the operator's machine with secrets
from a password manager" and left a CI deploy-on-tag open for M3. A final
independent review (2026-11-04) showed that the operating-system account
split alone protects secrets at rest but not the deploy path, which
executes repository code with those secrets in the environment.

## Options

1. **ADR-0006 as written:** production host from M0, one Kamal
   destination, a possible CI deploy at M3.
2. **A rehearsal destination, human-only production:** a throwaway
   rehearsal host in the slices that need one (`ensaio`, hostname
   `ensaio.rafasouza.dev.br`, hourly billing, cents per session) created
   by the implementing session from the same host definition as
   production, with rehearsal-only credentials; the production host created
   at the M3 soak and deployed only by the owner from a separate operator
   account, with a review of the deploy-path files before each deploy.
3. **CI deploys production** on a tag with repository secrets: cheapest in
   human time, but any workflow the agent pushes can read the secrets
   (GitHub has no per-workflow secret scope), so the agent would hold the
   production deploy.

## Decision

Option 2.

- Kamal has two configurations: the base `config/deploy.yml` (production)
  and the destination `ensaio` (`config/deploy.ensaio.yml`), differing in
  hostname, host and key (read from the environment on `ensaio`) and the
  model adapter default (`MODEL_ADAPTER=fake` on `ensaio`; the dev/eval
  key when a real-model rehearsal is wanted; never the production key).
  `APP_HOST` drives hosts, Origin, cable origins and links. `bin/deploy`
  knows only `-d ensaio`.
- M0 is done when `bin/deploy -d ensaio` (running `kamal setup` on a fresh
  host) puts a green `main` on the rehearsal hostname with TLS; the host
  is deleted afterwards. One host definition, `ops/cloud-init.yml`
  (declarative cloud-init modules, no script), creates every rehearsal
  host through the provider's CLI and the production VM at the M3 soak,
  so every rehearsal exercises the production host definition.
- Production deploys are run only by a human from the operator account.
  The production path executes no repository code outside the reviewed
  deploy-path files (`config/deploy.yml`, `.kamal/secrets` with references
  only, `Dockerfile`, `.dockerignore`, `package.json`, `package-lock.json`,
  `.mise.toml`/`.tool-versions`): Kamal is a pinned global gem invoked
  directly, the repo ships no `.kamal/hooks`, and the operator reviews the
  diff of those files between the deployed SHA and `origin/main` before
  fast-forwarding and deploying (SR-38).
- No Rails credentials file: every runtime secret is an environment
  variable injected by Kamal from the destination's env file. Production
  values are generated by the owner in the operator account; the rehearsal
  set by the session. One Console workspace and key per purpose
  (production app; dev/eval).
- The image is built on the workstation and reaches the host through
  Kamal's local registry over the SSH connection (no registry account; if
  the installed Kamal cannot cover the accessory or the host this way, two
  Docker Hub accounts, one per Unix account, are the fallback); the tag is
  the git SHA; rehearsal images are never promoted.
- CI never deploys in V1. The deploy-on-tag option of ADR-0006 is closed
  as **no**: production deploys stay human by design.
- **MVP amendment (2026-11-09, owner-approved).** Until M3 there is no
  production host and no operator account: the `ensaio` destination is one
  host created once from `ops/cloud-init.yml` on the reserved IP and kept,
  with `APP_HOST=balcao.rafasouza.dev.br`, the real model adapter on the
  spend-limited dev/eval key and the demo number's Meta values, deployed by
  the implementing session with `bin/deploy -d ensaio`. The per-slice
  rehearsal flow (create, deploy, destroy) is suspended until M3, when the
  production host takes the demo name, the MVP host is destroyed and
  `ensaio.rafasouza.dev.br` points at the reserved IP. The security
  argument of this ADR is unchanged; it starts applying at M3, and the
  threat model's R5 names what the MVP accepts meanwhile. Reason: the
  owner's two-week demo (design §9) cannot carry the operator account's
  set-up hours.
- Budget check against Hetzner's prices of 2026-11-04: CX23 (2 vCPU, 4 GB,
  40 GB) at €5.99/month incl. IPv4 fits the US$ 10 ceiling of ADR-0006;
  the Regular Performance line for the same box (€19.99) does not, so if
  CX23 is out of stock the location changes, not the plan. A rehearsal
  session costs cents; nothing bills while the project pauses before M3.

## Consequences

- The brief, design §8 and §9, and the threat model (T8, A4a/A4b, SR-24,
  SR-25, SR-26, SR-29, SR-37, SR-38, R5) carry the detail.
- The rehearsal hostname is public and found through certificate logs
  within minutes: it serves the fake model by default, sends `noindex`,
  pings no production monitor, and its visitor data dies with the host.
  Let's Encrypt allows five duplicate certificates per week for one
  hostname: the rehearsal flow counts the week's certificates on
  Certificate Transparency before deploying. The rehearsal `A` record
  points at a reserved IP, set once, so it never dangles and no DNS change
  is needed per rehearsal.
- The first real-model deploy may be a rehearsal with the dev/eval key,
  not production.
- The owner carries a small recurring ritual: the deploy-path review, the
  end-of-session resource check of the rehearsal project, a monthly glance
  at its cost.
- Reversal: if the owner ever wants CI deploys, that is a new ADR with the
  secret handling (environments, required reviewers, a deploy token the
  agent cannot read) worked out first.
